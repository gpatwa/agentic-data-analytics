# Per-user pass-through: independent security review (2026-11-20)

Status: **review only. Nothing is built, approved or tested live.** Reviewer: an agent that did not write `docs/design/PER_USER_PASSTHROUGH_DESIGN.md`. This is advisory; it is **not** the independent human review or penetration test (criterion 12 of `CONNECT-MODE-threat-model.md`) and approves no gate. Building pass-through (item H) is not approved. Paths below are under `services/analytics-api/` unless stated.

**Numbering.** The brief said to continue at T26, but T26 to T29 are already taken in `CONNECT-MODE-threat-model.md` (standing role, wrong-account sign-in, registration script, client credential). The new threats here are **T30 to T40**; fold them into that table when accepted.

## 1. Verdict

**Sound with named changes. Not yet buildable as written.** Option C (the user's token runs only the certified, compiled statement; fail closed; key everything by user; switch default off) is the right shape, and its seven preconditions are the right ones. But the design describes the code as if identity were a per-request argument, and it is not: identity is resolved **per tenant**, and several places hand a user's rows or a user's gateway to someone else. Six changes must be in the design before a build is approved:

- **N1. A per-run identity binding.** The design's "who runs it" must be one explicit object (requester, warehouse subject, token handle, mode) created once and carried by the run. See T32, T37, F1, F4.
- **N2. Resume as the requester, never the reviewer.** After a review approval the run is advanced with the **reviewer's** identity today (F2). Pass-through needs the requester's token or a refusal.
- **N3. Control query and execute on the same identity.** The design puts "everything not an answer" on the principal, but the control-totals query is part of answer validation and would mismatch every filtered user (F5). Dry-run is also not separable: `execute` runs its own `EXPLAIN` in the same session (F6).
- **N4. Remove the tenant-keyed rebuild hook and gateway cache for pass-through.** They are the concrete cross-user leak paths (T33, F3).
- **N5. A subject-mapping rule** between the product's user (Entra `oid`) and the warehouse's user, checked at sign-in and again on every run (T37). This is an owner decision.
- **N6. Revocation semantics stated**: what "revoked" means, how fast, and that no stored answer survives it (T35).

**What I could not verify:** nothing here ran against Databricks, an identity provider or a real vault. Vendor claims (token lifetime, refresh and revocation, whether a refresh token is issued, how a workspace maps an Entra user to a workspace user, whether row filters apply to `EXPLAIN COST`) are **unverified general knowledge** and are marked *check*. I read the Python under `app/` and the three docs; I did not read the web app, the Terraform, `packages/` beyond two contracts, or run any test. Ratings are judgement.

## 3. Concrete code findings

**Guards that already hold (verified):** run ids bind tenant and user and are HMAC-keyed outside dev (`analyze_service.py:91-93,150`; `pilot_wiring.py:380`); only the requester gets rows (`analyze_service.py:306`); a colleague cannot read a run (`:163`); no cross-run result cache exists; evidence holds fingerprints, counts and codes only (`runtime/evidence.py:131-141`); driver errors are reduced to a type (`warehouse_gateway.py:160-163`); every statement still passes `validate_read_only_sql` against the connection's table allow-list (`warehouse_gateway.py:_check`); the vault never echoes errors (`vault.py:53-87`); sign-in state, binding cookie, PKCE and redirect controls (`oauth.py`); the gateway is built per tenant from that tenant's record only (`connect/gateway.py:25-52`).

**Where the code would have to change:**

- **F1. Identity is not an input to gateway resolution.** `connected_gateway_resolver`/`connected_assets_resolver` take only `tenant_id` (`connect/runtime_gateway.py:32`; `connect/tenant_assets.py:52-56,73`), and `GovernedRuntime._tenant` / `_gateway` call them with a tenant (`runtime/pilot_wiring.py:149-165`). Needs the run's binding object (N1), with a mode check first so a pass-through connection can never return the principal's gateway.
- **F2. Review resume uses the reviewer.** `decide_review` ends in `_resume(identity, state)` (`analyze_service.py:226`), and `_resume` builds the runner for that identity (`:244-259`), so the `execute` node and gateway come from the reviewer. Pass-through: resume by the requester's binding, or park the run until the requester returns (consent to run is a second, user-visible step).
- **F3. Cache and store inventory (every one checked in `app/`).**
  - `ExecutionResultStore._rebuilders` per tenant, overwritten per run: `execution/bridge.py:29-31,101-102`; used by `resume` (`:63-82`) and by `result_validation_node` (`runtime/result_stage.py:39`). **Leak path.** Remove, or key by `run_id` with the run's own handle.
  - `connected_gateway_resolver` cache `(tenant, connection, secret version)`, 300 s: `connect/runtime_gateway.py:30,45-53`. Would hold one user's gateway for all. Bypass for pass-through.
  - `_tenant_breakers` per tenant: `pilot_wiring.py:131,151,165`. Cross-user availability (T40).
  - `ExecutionResultStore._results` (2,000 entries, process-local): `bridge.py:23`; `ExplanationStore`: `runtime/explain_stage.py:19-23`; `ValidationReportStore`: `runtime/evidence_sealer.py:24-28`. Keyed by run, so safe against another user, but they are the replay source for T35: drop on revoke and cap lifetime.
  - `CompiledPlanStore` (SQL and bound policy values, durable) and `PolicyValueStore` (durable, includes identity claims): `runtime/governed_stages.py:33,140`. Not cross-user, but a token must never enter them.
  - `InMemoryDraftCache`: `ontology_draft/drafter.py:102-121`. Drafting stays on the principal; add a guard that it never receives a user session.
  - Not found: any cost-estimate cache, any dedupe across runs. Not checked: web-app client caches, `packages/`, infrastructure caches (CDN, API gateway).
- **F4. Token type.** `AdminToken` (`connect/token.py`) is not single-use and caps at 300 s; add a `UserToken` and a one-shot `reveal`. The driver takes a bare string at `execution/warehouse_sessions.py:112,347`; a per-user session needs a credentials provider that reads the handle at connect time.
- **F5. Control totals use the tenant gateway.** `pilot_wiring.py:211-219` via `result_stage.py:43`. Must follow the result's identity (N3).
- **F6. `execute` does its own `EXPLAIN`** in the executing session (`warehouse_gateway.py:130-136`), so "dry-run on the principal" in the design table is not what happens: only `estimate_node` (`pilot_wiring.py:189-195`) does. A user session must be allowed to run `EXPLAIN COST` (*check* on a row-filtered table) or the cost bound fails closed for pass-through.
- **F7. OAuth is admin- and Snowflake-shaped.** Host check `oauth.py:154`, redirect to `/connect/review/{setup_id}`, handoff keyed by setup (`:272`), scope `session:role:` (`:~330`). A user flow needs a Databricks config, a per-user key `(tenant, user, connection)`, and the T36 screen. `AuthSession.user_id` (`oauth.py:~190`) exists but is never checked against the token's subject (T37).
- **F8. Evidence lacks the executing identity.** Add `executed_as` and `subject_hash` to the envelope (`packages/platform_contracts/evidence.py`; `runtime/evidence.py:131-141`) before pass-through produces its first answer (T34, T39).
- **F9. Caller kinds.** `caller_kind` marks delegated and app-only callers as `agent` (`security/identity.py:70-75`; `entra.py:81-86`); pass-through must refuse them explicitly.

## 4. Tests to write first (ordered by the risk they retire)

All on fakes first; none needs a network.

1. **No fallback to the principal** (T32a): pass-through on, no or expired user token: every entry point refuses with a stable code; the fake principal gateway records zero calls.
2. **Two users, one tenant, no sharing** (T33): A then B; evict A's result; A's rebuild never uses B's gateway; two users never get the same gateway object; results never cross.
3. **Reviewer resume** (T32b): a run approved by a reviewer executes only as the requester, or refuses.
4. **Token sentinel scan** (T30, T34): a sentinel token and a sentinel row value appear nowhere in logs, records, evidence, errors, `claims`, policy values, on success and every failure path.
5. **Subject binding** (T37): wrong subject at sign-in and at run time refused; rename and re-use cases.
6. **Revocation** (T35): revoke after a terminal answer, while paused, and on sign-out; no replay of stored rows.
7. **Idempotency across users and bindings** (T38), with and without the server key.
8. **Control totals and oracle identity** (T39): a row-subset user passes validation; an oracle never compares across identities.
9. **Breaker isolation and auth-failure classification** (T40).
10. **Consent flow** (T36): cross-session callback, scope allow-list, registration equals approved values.
11. **Vault custody** (T31) if any refresh token is kept: per-user names, purge on revoke, no read after offboard.

## 5. What needs the owner

**Decisions (none made here):**

1. **Build C, defer or never** (the design's recommendation, defer until a customer names row-level security, stands; this review does not change it).
2. **Refresh tokens: none in v1** (recommended; re-sign-in, fail closed) or a stored token (T31). Whichever, state the maximum answer staleness after revocation (T35).
3. **The subject mapping** between the Entra `oid` and the warehouse user, and who may re-bind it (T37).
4. **Whether a control-total check runs under row filters** or is replaced by a recorded `unverifiable` code (T39).
5. **Whether agents and delegated callers may use pass-through** (recommended: no) (F9).
6. **Approval of the six named changes (N1 to N6)** as design amendments before any build.

**Must be verified on a real identity provider and workspace (a live step, needs the owner's approval of the exact statements):**

- Databricks user-to-machine OAuth: token lifetime, whether a refresh token is issued, whether vendor-side revocation ends an issued access token early, and whether an Entra-issued token or a Databricks-issued one is used.
- How the workspace maps the signed-in user (SCIM user, email) and what `current_user()` returns; what happens on rename or email re-use.
- That a row filter and a column mask apply to the user's session for the **compiled** statement, for `EXPLAIN COST`, and for the control query, with two users.
- That a user's session cannot read a table outside the connection's table allow-list the gateway enforces (the allow-list is ours; the grants are theirs).
- Key Vault soft-delete, purge protection and access policy for any stored secret.
- A real consent screen: what scope the user sees and whether it can be narrowed to read-only SQL.

## Not verified

Everything about vendor behaviour (all *check* items). Line numbers marked `~` are approximate. I did not run the test suite. I did not read the web app, infrastructure code, or the rest of `packages/`, so a cache outside `app/` would be missed. The design's claim that the product-run sign-in is "public client with PKCE" is verified in `oauth.py`; its claim that it is reusable for users is not (F7).
