**The registration script is the product's own** (`generate_registration`) with one declared sandbox deviation: the sign-in comes back to `http://localhost` and the integration sets `OAUTH_ALLOW_NON_TLS_REDIRECT_URI = TRUE`. The network policy is attached **only to the OAuth integration**; no statement here changes the account's or any user's network policy (a stop rule refuses one). Not verified against a live account: `CREATE NETWORK POLICY`, `NETWORK_POLICY` on the integration, `ALTER NETWORK POLICY`, and `CURRENT_IP_ADDRESS()` as the Compass address.

### What the admin is told for that script

- Register Compass once, so it can set up read-only access for you later without you running a script each time.
- Creates a sign-in for Compass (OAuth) that works only when one of your named users signs in and approves. It issues no long-lived tokens: each sign-in lasts 10 minutes and cannot be refreshed. Admin roles (ACCOUNTADMIN, SECURITYADMIN, ORGADMIN) cannot use it.
- Creates a setup role that can only create read-only roles and users and pass on read access to the 2 table(s) in 1 schema(s) of COMPASS_E2E_DB_A1B2C3D4 that you name here. That is the ceiling: it can never grant more.
- While signed in as the setup role, Compass can read those tables as well. Compass uses it only during a setup you approve.
- Allows the setup role to be used by 1 user(s) you name, and the sign-in only from 1 Compass network address(es).
- Adds a small warehouse capped at 1 credit(s) that suspends after 60 seconds; every connection Compass sets up uses it.
- To remove all of this later, run the removal script. After the last statement runs, give Compass the client id it shows (not a secret).
- Sandbox only: the sign-in comes back to an address on the developer's own machine over plain http. A real deployment never does this.
