# A realistic data source for the production experience: options and a recommendation (2026-11-19)

Status: **research and a recommendation for the owner to decide; nothing is loaded or run.** Loading data into the owner's Snowflake or Databricks account is a live step that needs explicit approval with the statements shown first (CLAUDE.md). Facts below come from vendor and dataset documentation read on 2026-11-19 and are **not verified on an account**; items marked *verify* are checks to make before relying on them. It supersedes the "demo data" question deferred on 2026-11-18, and extends `REFERENCE_DATA_DEMO_PLAN.md` (R1 built: three small synthetic tables).

## What "realistic" has to mean here

The validation so far used a 30-row synthetic table. A production experience needs, in this order of importance for what we are testing:

1. **Real distributions and mess**: nulls, outliers, skew, odd types, dates that run to the edge of the data, categories nobody planned.
2. **Scale** big enough that the cost estimate, the row cap, the timeout and small-group suppression actually bite (millions of rows, not thousands).
3. **A shape the product can use today**: the compiler handles one dataset per query, with no joins and no ratios. A source that needs joins is usable only through a denormalised view or table, which is also how enterprises expose data to BI (a "gold" layer).
4. **Available on both engines** with the same rows, so parity can be checked against an independent oracle.
5. **Safe to use publicly**: a licence that allows a product demo, and no real person in it.
6. **Cheap and repeatable**: loadable and removable by a script, with a checksum.

## Two findings that change the plan

1. **Built-in shared sample databases probably cannot be granted table by table.** Our connection model gives a read-only identity `SELECT` on exactly the tables the admin names. Snowflake's sample database is a shared database (consumers receive imported privileges, not per-object grants), and Databricks' `samples` catalog is read-only and system-owned. *Verify both.* If true, the product cannot connect to them the way it connects to a customer's tables; the realistic path is to **copy the rows into our own database or catalog** (a persistent reference schema, as `REFERENCE_DATA_DEMO_PLAN.md` R4 proposes) and connect to that.
2. **The compiler's single-dataset limit decides the shape.** The TLC trips table is already one wide fact table, so it is usable as is. Olist and the TPC sets need a denormalised table or view built by the admin, which is realistic, but the view is part of what we certify, and every question that truly needs a join is out of scope until a join packet exists.

## Recommendation

**Primary: the NYC TLC yellow-taxi trips**, loaded as one wide table (plus a small taxi-zone lookup folded in as columns) into a **persistent, Compass-owned reference schema on both Snowflake and Databricks**, a few months to a year (about 10 to 40 million rows), with an independent oracle (the same Parquet files read by plain Python or DuckDB) and a checksum table. Why: it is real data with real mess and skew, it fits the compiler without a join, it is large enough for the cost estimate, row cap, timeout and small-group suppression to matter, the same files load identically on both engines, and Databricks already ships the same domain as a smoke test. Realistic questions that work today: trips and fares by month, borough or zone, payment type and hour of day; tip share by payment type (needs the ratio packet; counts and sums work now).

**Secondary, for commerce-shaped questions: Olist as a denormalised order-items view**, **internal validation only** until the Kaggle licence is checked, because it continues the existing certified contract and tests.

**Keep, for what real data cannot show:** the R1 synthetic tables (personal-data redaction, small cohorts, poisoned comments).

**Scale and cost checks only:** TPC-H or TPC-DS, loaded or copied, never presented as production-like data.

What production still needs that no static dataset gives: schema drift, late and duplicate data, many concurrent users, and a customer's own naming and history. Those are pilot-with-a-design-partner tests, not data choices; the page copy should keep saying so.

## Decisions for you

1. **Pick the primary source** (recommended: NYC TLC yellow taxi) and the size (recommended: one year, then trim by what the cost estimate shows).
2. **Where it lives:** Compass-owned reference schemas (recommended), versus isolated permanent schemas in the existing personal accounts for now.
3. **Olist for public use:** I check the Kaggle licence before it appears anywhere public (recommended), and treat it as internal until then.
4. **Order:** DuckDB or PostgreSQL first for the oracle and contract (offline, no approval), then Snowflake and Databricks together as one approved live step with the statements shown first.

Nothing is certified here: a contract on this data is drafted by the drafter and certified by a person, as for the sandbox.
